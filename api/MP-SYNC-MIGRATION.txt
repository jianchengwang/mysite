最小切换
1. 客户端先适配并读取受认证保护的 GET /api/mp/draft/capabilities。
2. 操作者在既有安全配置中设置 MP_DRAFT_MODE=sync、MP_REDIS_URL（仅服务端），MP_DRAFT_CACHE_TTL 默认24h，可设1h–48h。本包不含任何真实环境文件。
3. 新操作的 POST /api/mp/draft 必须 X-MP-Draft-API: 2，以及 Idempotency-Key: v2.<独立新操作标识>（总长16–128，沿用字符白名单）。缺版本头428；缺v2.前缀400。旧客户端停止写入并迁移，没有回退到MySQL队列。
4. 保持原 JSON、认证、CORS、HTML/图片/SSRF限制。调用方 HTTP 总等待预算至少60s；服务端处理预算45s，路由写截止55s。需要核实全部代理/外网链路的实际超时，不能假设现有代理已满足。
5. 只在 HTTP200、api_version=2、status=succeeded、provider_success=true、有有效media_id时报告“已新增草稿”。成功返回 article_count=1。微信成功回包无errcode时字段为null；收到实际0才返回0。
6. client timeout/断线/502/504/409后，优先用同一个 Idempotency-Key 查询 GET /api/mp/draft/result。不要生成新key自动重发，不把任何20x或上传素材成功当草稿成功。结果查询返回操作对应的HTTP状态，不是统一200。
7. GET /api/tasks/{旧ID}、GET /api/mp/draft/diagnostics 保留，继续访问旧MySQL历史；只读diagnostics不包含新的同步操作，需要通过request_id日志或短期结果查询定位。旧任务的key不可加v2.前缀后重发。

结果语义
成功：200 succeeded / provider_success=true / media_id /实际errcode（可null）。
明确微信拒绝：502 failed / provider_success=false /真实非零errcode；有已成功上传则partial_success=true。
微信写入响应丢失、5xx、非法响应或缺必要回执：502（预算耗尽504）needs_reconciliation，retryable=false。若 draft/add 已尝试则 provider_success=null；若仅图片上传结果不明、draft/add未调用则false。
并发同键同正文：409 processing；查询或等待，不发第二次远端写入。
同键不同正文：409冲突；不给另一篇正文重用key。
缓存不可用：503，预留确认前不做远端写入。预留响应丢失也503，不假设没预留；查询同键可能processing。
确认微信新增成功但最后Redis存回执失败：仍200 true +有效media_id +cache_warning=true；不能谎报草稿失败。旧pending记录保留，禁止因缓存失败重发。
进程中断、记录仍pending且执行截止已过：409 needs_reconciliation；不接管、不重排。
404无短期回执：不证明远端没有成功，也不授予再次写入许可。
remote_write_possible 表示持久化的保守写入意图；可能为true但实际未写入，不把它当微信成功证据。

短期幂等边界（必须告知调用方）
Redis只记录账号+幂等键的SHA256键、正文规范化请求hash、opaque owner/request_id、截止/过期时间和脱敏紧凑回执；不放正文、标题、摘要、PreparedContent、图片字节/base64、原始key、token、secret或原始errmsg。
SET NX +到期为唯一预留；Redis7 Lua核对owner/hash，原子更新并KEEPTTL，不延长最初期限，不删除pending、不重新取得所有权。每次远端写入前缓存保守pending意图，已确认图片回执存入后再推进。所有图片仍先下载解码，再写微信。
只有在记录持续保留期间，才能阻止同键重复；到期、驱逐、重启造成数据丢失或清库会失去证据，不是永久exactly-once。部署前应核实所选Redis实例的隔离、noeviction/容量和持久化策略，本轮不修改现有Redis设置。即便启用持久化，也不宣称绝对不丢数据。缓存恢复但记录已丢时，服务不能识别曾用key；客户端不能自动把404或空库当作重新提交许可。
不同key视为不同独立操作；相同正文用不同key不会全局去重。新路径仅在单次请求按图片hash+用途复用，不再读取/写入MySQL跨任务媒体账本；跨请求素材复用可另议，不为此另建队列或长期账本。
正文仅在请求处理期间驻留内存；成功/失败/超时后不写数据库。原来真实任务与正文保持原样，不做删除、迁移清库或重新发送。

Content-only layout update (content_only_cas_v1):
POST /api/mp/draft/update, authenticated exactly like the existing draft API.
X-MP-Draft-API: 2; Idempotency-Key: v2.layout.<unique operation> (or v2.update.).
Body: media_id, index:0, expected_content_sha256 (lowercase SHA256 of exact current
UTF-8 HTML content), content. No metadata fields are accepted. Only existing
single-article drafts are supported. The server performs official draft/get,
compares the exact content hash, and permits only p.style changes; all parsed
text nodes, other HTML tokens and attributes must remain equivalent. It sends
all freshly observed article metadata, except temporary url/thumb_url, unchanged
to official draft/update, replacing only content. It verifies exact content and
all nonvolatile metadata through a second official get before status succeeded.
The hash mismatch is HTTP409 precondition_failed before any update. This is a
fresh-read precondition, not an atomic provider CAS; editing in WeChat between
the fresh read and the write is not locked by the provider API. Coordinate edits
while the authorized update runs. Official draft/add is never used by this route.
The existing Redis receipt reservation and write-intent rules apply. For response
loss, unknown outcome, interruption or cache miss, never send another update;
query the same key through GET /api/mp/draft/result and reconcile official get.
Provider-acknowledged update plus failed/different readback returns retained
media_id, provider_success true and needs_reconciliation, not success. No new
MySQL task or body/metadata cache is written.
