上一课里，A1的答案已经写好了：把“周五前提交提纲”交给atlas项目的lin。现在要把这道题送进训练程序。

你可能觉得，把输入和答案存成JSON就行。麻烦在后面：训练程序读到的不是网页上的句子，而是一串数字。如果中间漏了负责人，或者把回答截掉一半，原来写对的样本也会变成一道坏题。

这次只跟着A1走一遍。先保存它，再把规则、请求和答案排好，最后看看哪些数字会参与训练。Notebook默认只用CPU和Python标准库。

## 先保存一条以后还能看懂的记录

运行开头的准备单元后，在 `data[0]` 可以找到A1。它包含这几部分：

```json
{
  "sample_id": "A1",
  "source_group": "A",
  "case_type": "complete",
  "tools_enabled": true,
  "messages": [{"role": "user", "content": "把“周五前提交提纲”发给 atlas 项目的 lin。"}],
  "target": {"decision": "call", "tool": "dispatch_note", "arguments": {"project": "atlas", "owner": "lin", "text": "周五前提交提纲"}},
  "annotation_version": "0.1",
  "split": "train"
}
```

`sample_id` 让你能找到这道题；`source_group` 记住它和A2、A3来自同一个场景；`annotation_version` 表示答案依据哪一版规则写成。`split` 说明这条准备用来训练。它们帮助人追查文件，不是用户请求的一部分。

试想把整段JSON都喂给模型：`case_type` 已经写着complete，等于暗示“这道题信息完整”。如果以后把缺参题标成missing，模型甚至不用认真读句子，就能知道该追问。这会让练习成绩好看，却帮不了真正的聊天入口。因此代码里的 `model_input` 只挑出开关、工具说明和消息。

运行 `audit` 所在单元。它先检查ID是否重复、开关是否真的是布尔值、答案格式是否正确，再检查同一来源组有没有被分到两边。代码还会故意把A2的输入换成A1的输入，却保留A2的追问答案。这样“同一道题有两个矛盾答案”，应该被发现。

这里需要区分两件事：检查器能发现同输入答案冲突，但不一定知道每个自然语言参数有没有依据。把A1的owner标成mei仍然可能格式正确。后者要回到原句核对，不能只看程序打印了“通过”。

## 写进文件，再读回来

接下来代码按train、validation、test分别写JSONL文件。JSONL就是一行一条JSON记录。相比把整个数据集装进一个大数组，它更方便逐条读取和检查坏行。

这里没有新造数据，还是第一课的12题。写完后代码把每个文件再读回来，与内存中的记录比较。你可以在当前Notebook会话里运行 `print((OUT/'train.jsonl').read_text())` 看看实际保存了什么。

旁边的 `manifest` 是一份文件说明，记录条数、来源组、类别数量和文件哈希。哈希可以理解为文件的指纹：改一个字，计算结果通常就会变。它用来检查“这次用的还是不是那份数据”，不能证明里面没有相似题，也不能判断答案对不对。

本课生成的是独立临时目录，不会覆盖你的Drive。想保存自己的实验，等检查完再复制出去。不要先攒了多个同名 `train.jsonl`，跑完才猜用的是哪个。

## A1在对话里应该排成什么样

先按人的视角看三段话：规则是谁给的、用户说了什么、正确回答是什么。对话模型常把这三种内容称为system、user、assistant。

| 位置 | A1在这一位置的内容 | 用处 |
|---|---|---|
| system | 工具已启用；发送需要owner、project、text，搜索需要project、query | 告诉模型当前应用条件 |
| user | 把“周五前提交提纲”发给 atlas 项目的 lin。 | 这次要处理的请求 |
| assistant | `{"decision":"call","tool":"dispatch_note","arguments":{"project":"atlas","owner":"lin","text":"周五前提交提纲"}}` | 训练时希望学到的回答 |

`tools_enabled` 来自应用，放在规则一侧。用户正文里的“工具已启用”不能替代它。这也是为什么前一课禁用题即使字段齐全，仍然不能发。

Notebook里的 `render(data[0])` 返回两段字符串：第一段到assistant开始的位置为止，第二段是答案。第一段通常叫prompt，可以先理解成“模型开口之前能看到的全部内容”。实际返回值是：

```text
<system>{"tools_enabled": true, "schema": {"dispatch_note": ["owner", "project", "text"], "search_notes": ["project", "query"]}}</system><user>把“周五前提交提纲”发给 atlas 项目的 lin。</user><assistant>
```

答案则是表格中的那段JSON，代码使用紧凑写法，不额外插入空格。

这里的 `<system>`、`<user>`、`<assistant>` 是为了看清顺序而写的教学标记。它没有承诺某个预训练模型认识这套写法。到了第3、4课真正加载Qwen时，会改用该模型自带的聊天模板。模板做的是同一件事——把消息排成模型训练时熟悉的形式——但具体分隔符不能随手照抄。

多轮题E1也经过相同函数。你可以运行 `print(render(data[9])[0])`，应该同时看到最初的请求和“负责人改为mei，其他不变”。如果只剩后一句，先修输入，不要去调整学习率。

## 文本变成数字后，A1还在吗

模型需要数字输入。把文本切成若干单位、给每个单位一个编号的程序叫tokenizer；切出来的单位叫token。真实tokenizer可能把一个词、一个汉字的一部分或一段符号编成一个token，字符数不等于token数。

本课选了一个容易检查的办法：先把文字编码成UTF-8字节，再给每个字节加1。这样0可以留作补齐空位的编号，257用来表示回答结束。这个教学tokenizer是可逆的，所以我们可以把数字转回文本，检查是不是原来的A1。

运行 `labeled` 所在单元。对当前A1，开头八个编号是：

```text
[61, 116, 122, 116, 117, 102, 110, 63]
```

它们对应 `<system>`。A1的prompt占220个教学token，答案加结束标记占120个，合起来340个。这些数字来自这份byte编码练习，不是Qwen的长度，也不能拿去估算Qwen显存。

现在看两个数组：`input_ids` 是完整输入编号；`labels` 是训练要对照的答案编号。A1在回答开始附近是这样：

| 位置 | input_ids | labels | 这里是什么 |
|---|---:|---:|---|
| 217 | 111 | -100 | assistant标记的一部分 |
| 218 | 117 | -100 | assistant标记的一部分 |
| 219 | 63 | -100 | 标记结尾的 `>` |
| 220 | 124 | 124 | 答案开头的 `{` |
| 221 | 35 | 35 | 答案里的引号 |
| 222 | 101 | 101 | decision的首字母d |

`-100`不是一个要让模型输出的词。这里约定它表示“这个位置不计入回答损失”。损失，也就是loss，是用来衡量模型对正确答案预测得有多差的数。提示部分不计分，答案部分计分。

## 用户请求不计分，模型还能看见它吗

能，而且必须看见。否则模型怎么知道这次的负责人是lin？

“能不能读取前文”和“哪个位置的错误参与计分”是两件事。`input_ids` 保留规则和请求；`labels` 把它们对应的位置写成-100，只是不要求模型把用户请求也当作待学习的回答复述一遍。

你可能还会问：答案都放进去了，不是直接抄吗？关键在预测顺序。预测答案第一个token `{` 时，模型只能使用它前面的规则和请求。预测后面的token时，才逐步看到正确答案已经走过的部分。这种训练时提供正确前文的方式叫teacher forcing。实际生成则要接着自己刚生成的内容往下写，所以训练loss低，不保证一次生成就完全正确。

现阶段先检查一件具体的事：从labels里挑出真正计分的编号，解码后是不是完整的答案JSON。代码已经做了这个断言。若只解出一个大括号，哪怕还有有效label，也不能说数据没问题。

## 字数太长，不能只剪到能跑

`labeled` 默认允许2048个教学token。调用 `labeled(data[0], 10)` 会失败，因为10个位置连请求都放不下。这是Notebook故意设置的检查：发现超长就停下来，不悄悄把尾部剪掉。

为什么不直接剪？答案就在尾部，右边截断可能把答案删没；从左边剪又可能丢掉工具开关或多轮更正的前文。要先看长在哪，再决定是否能删无关上下文。删完还要重新读一遍，确认答案仍然有依据。

一个batch里各题长度不同，也要补到同样宽度，代码把这一步叫 `collate`。补上的空位叫padding。`attention_mask` 用0标记这些空位，让它们不被当成正常输入；补位的labels写-100，不参与loss。

运行后面的pad/EOS检查。EOS就是结束标记。有些真实模型让padding与EOS共用同一个编号，不能一看到这个编号就全部忽略，否则真正的回答结尾也被抹掉了。正确做法是按位置判断哪些是补位。本课用一个很短的数组专门演示这件事。

最后看长度的中位数、90%位置和最大值。它们帮助你了解数据有多长。先知道长题是什么，再选长度上限，比先写一个熟悉的1024、随后接受所有截断更容易排错。

## 做完主线，再看下一token是怎样对齐的

这段稍微靠近训练实现，第一次读可以在跑完练习后回来。

A1的首个回答token在位置220，但预测它的输出来自位置219：模型看完位置219的 `>`，预测下一个位置该是什么。自定义loss里通常比较 `logits[t]` 和 `labels[t+1]`。logits可以理解为模型给所有可能下一个token的打分。

第4课的小模型自己做这个对齐；常见CausalLM模型则在内部完成。若模型已经移过一次，你再手动移一次，就会错一格。因此不能只看两个数组一样长，还要知道loss函数具体怎么用它们。

真实聊天模板也可能改变token边界。第4课会先断言：单独生成的prompt编号，确实是完整“prompt＋答案”编号的前缀，成立后再把前缀labels设为-100。失败时不要只取一个长度硬切。也有训练器能按模板提供的assistant区域生成mask，但那是另一条实现路线，本系列的代码主线先保留显式labels。

packing是把多条样本挤进一个长序列以减少空位。它会带来跨样本注意力和边界问题，先别为这12题增加复杂度。普通padding的正确性检查通过后，再在第5课讨论这类优化值不值得做。

## 现在试着回答三个问题

在 `YOUR_ANSWERS` 中填入三个字段。`logit_offset` 问的是首个回答token的预测位置相对它偏几格；`padding_label` 问补位是否计分；`overflow` 问超长时如何处理。答案放在后面的 `SOLUTIONS`。

对应答案是-1、-100和 `review_before_truncate`。如果第一项答错，拿上面的219和220位置再走一遍；如果第二项答错，回头区分“输入可见”和“参与计分”；如果第三项想选直接截断，先问自己被截掉的是无关聊天，还是负责人和答案。

做到这里，A1已经走完一趟：原始记录能保存和读回，规则与请求没有混入审计标签，数字可以还原成文本，回答完整地留在labels中。下一课就可以把同样的请求交给未微调模型，看看它到底会怎么答。

模板接口可参考[固定版本Transformers聊天模板文档](https://huggingface.co/docs/transformers/v4.57.3/chat_templating)。本文的byte编号只服务于讲解，真正的tokenizer和模板要跟随所加载的模型版本。
