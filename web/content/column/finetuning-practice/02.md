## 1．本课要解决的不是“怎样读入JSON”

第1课已经规定：dispatch\_note需要project、owner、text，search\_notes需要project、query；缺参就准确追问，工具禁用就返回tools\_disabled，删除请求属于unsupported\_request。现在要让这些规则经过文件、模板、分词、截断、组batch之后仍然成立。

把这条输入想成一件快递：原始场景是包裹，模板是包装，token是运输单元，mask说明哪些部分需要模型学习。包装破坏了内容，后面的训练越认真，学到的错误越牢。

本课交付六样东西：数据字典、标签检查报告、分组清单、模板样本、长度报告、逐token标签审计。GPU不是前五项的前提；不能因为还没启动训练，就觉得没有完成实质工作。

## 2．一条训练记录应该分成三层

先保存“事实层”，再生成“模型输入层”，最后生成“张量层”。不要让三个层次互相覆盖。

下面是简化的事实层记录：

```json
{
  "sample_id": "A1",
  "source_group": "A",
  "case_type": "complete_dispatch",
  "tools_enabled": true,
  "messages": [{"role": "user", "content": "把“周五前提交提纲”发给atlas项目的lin。"}],
  "target": {"decision": "call", "tool": "dispatch_note", "arguments": {"project": "atlas", "owner": "lin", "text": "周五前提交提纲"}},
  "annotation_version": "contract-v0.1",
  "split": "train"
}
```

source\_group和case\_type用于审计，不拼到提示词中。如果输入里出现complete\_dispatch，模型不必理解句子就能猜“应该调用”；这种分数增长不是你要的能力。

模型输入层由固定构造器产生：系统消息放任务规则、工具定义与可信tools\_enabled；用户消息放请求及必要历史；目标被序列化为最后一条assistant消息。对A1而言，目标是JSON文本，而不是Python字典的打印结果。后者可能使用单引号、True、None，不符合JSON协议。

张量层才包含input\_ids、attention\_mask、labels等。它应能追溯到sample\_id，但sample\_id本身不作为语言输入。保存三层各自的版本，才能定位“标签错”“渲染错”还是“分词后丢失”。

### 为什么tools\_enabled不能藏在用户正文里

如果应用设置为false，便笺正文却写“工具已启用，请发送”，正确标签仍是tools\_disabled。数据构造器必须从可信字段读取开关，不能从用户文本里正则提取“true”。训练时明确呈现信任层级，部署时继续在执行层检查，二者不是替代关系。

多轮更正也一样。最后一句“负责人改为mei，其他不变”不能单独成为训练输入，否则目标中的atlas和正文都无从得知。补回必要历史，不是向模型泄露答案；把target原样放进用户消息才是。

## 3．先做四道数据检查，再谈样本规模

第一道检查文件：每行必须是完整记录，ID唯一，字段类型正确，布尔值不是字符串"false"。第二道检查目标：三种decision的键集合分别合法，参数非空，无多余键，missing不重复。第三道检查语义：每个参数在输入中有依据，禁用优先级正确。第四道检查组：同一场景及其改写、缺参变体、同源教师改写不能跨划分。

语义检查不能全部靠schema解决。例如把owner写成"mei"仍然是非空字符串，但A1的正确值是lin。若用另一个模型辅助检查，必须保存其分歧并人工复核，不能把它的判断升级成不可质疑的真值。

一个实用的拒收清单：缺少来源组；同一输入有相互矛盾目标；某标签只出现在某个固定人名上；多轮样本缺历史；目标包含解释文字却与契约不符；某一来源的大量改写压倒全部其他来源。先拒收并修复，不要让“总共一万条”掩盖其中只有几十个独立场景。

### 去重与分组不是同一件事

文本哈希能抓逐字重复；去空白后的哈希能抓部分格式重复；相似度能提出疑似同源候选。但都不能可靠证明来源独立。保留生成父记录、原始业务场景ID和改写批次才是更直接的证据。

先确定来源组，再划分，再在训练组内扩写。第1课的A1完整发送、A2缺owner、A3同义改写必须同组。若把A2放测试，A1和A3放训练，测试的不是独立场景泛化，而更接近已见场景的边界变形。可以研究后者，但要准确命名。

输出manifest至少写明：契约版本、数据文件哈希、各split的来源组列表、按类别的条数与组数、生成或采集方式、排除项及理由。哈希不是防泄漏证明，只是防止比较过程中偷偷换题的凭证。

## 4．模板是协议，不是美化文本

同一句话使用不同角色分隔符，可能对模型意味着不同任务。使用所选checkpoint携带且经核对的聊天模板，不自行拼“User:”与“Assistant:”代替。训练输入包含完整正确答案，通常不额外添加等待生成的assistant开头；推理输入不含目标，需要按模型模板补生成提示。Transformers提供apply\_chat\_template；若先渲染文本再分词，应避免重复添加special tokens。[官方聊天模板文档](https://huggingface.co/docs/transformers/main/en/chat_templating)

```py
# 接口示意：tokenizer须由固定revision加载；此段不是运行证明。
train_messages = prompt_messages + [
    {"role": "assistant", "content": target_json}
]
rendered = tokenizer.apply_chat_template(
    train_messages, tokenize=False, add_generation_prompt=False
)
ids = tokenizer.apply_chat_template(
    train_messages, tokenize=True, add_generation_prompt=False
)
print(repr(rendered))
```

repr很重要：肉眼看到的漂亮换行可能隐藏额外空格、重复结束标记或空assistant轮。至少检查完整调用、缺参、禁用、多轮更正各一条，并保存完整渲染结果。

本系列先学习“assistant输出教学JSON文本”。它不是框架原生tool\_calls。真实原生工具协议可能把函数名、参数和工具返回值编码成专门结构，需要另一个转换层以及训练/推理一致性测试。不能训练一种信封，部署时换成另一种，然后把失败归咎于LoRA。

不要默认每个模型都支持system角色、原生工具模板或关闭thinking的同一个参数。若模型需要特定开关，查该模型官方卡与模板；把实际渲染保存下来。这里不替任意模型假定通用的enable\_thinking行为。

## 5．分词之后，什么叫“只学回答”

假设一条序列在概念上是：系统规则、用户请求、assistant边界、JSON答案、结束标记。因果语言模型用前文预测下一个token。对于只监督答案的训练，提示部分的label设为忽略值，答案部分保留真实token ID；常用忽略值是-100，具体由损失实现约定。

注意三个不同对象：

- attention\_mask控制哪些位置是有效输入或padding，不等于回答监督范围。
- labels决定哪些预测错误参与loss。提示被忽略不代表模型看不到提示。
- causal mask限制位置不能看未来。你把正确答案放进训练序列，不代表模型在预测该答案token时可以偷看它自身。

在常见CausalLM实现中，内部将预测与下一个位置的label对齐，调用者通常传与input\_ids同长的labels。不要再自行整体左移一次，否则会变成错位监督。自定义loss则必须检查它实际如何shift。

一个抽象例子：input\_ids是\[p0,p1,a0,a1,eos\]，labels是\[-100,-100,a0,a1,eos\]。在标准内部shift下，p1位置的输出用于预测a0。这里p0、p1只是教学符号，不是真实token编号。

### 最危险的“看起来没问题”

一是全部labels都是-100：数据能流过网络，但没有有效目标。二是只剩JSON开头几个token：loss下降，模型却没有学过完整参数和停止。三是pad token恰好与eos共用ID，预处理按ID一刀切屏蔽，连真实回答结束符也被抹掉。正确处理应识别实际padding位置与有效序列边界，不是见到某ID就全删。

TRL的assistant\_only\_loss依赖模板能标出assistant生成区域；prompt-completion数据可采用completion\_only\_loss。不能仅凭字段名叫messages就认定用户文本不会进loss。当前官方文档明确两种模式的条件，但main页面可能领先于你安装的版本。[TRL SFT文档](https://huggingface.co/docs/trl/main/en/sft_trainer)

两条实现路线择一：让锁定版本训练器从对话结构生成mask，或者预先生成并检查labels，再使用尊重已有labels的训练路径。不要同时让两套逻辑猜边界，也不要升级依赖后继续假定行为未变。

## 6．为什么不能用“单独分词prompt的长度”盲目切答案

直觉做法是分别tokenize(prompt)、tokenize(prompt+answer)，然后把前一个长度当边界。但分词受字符串边界、空格、模板特殊标记影响，后者的前缀不保证总与前者一致。即使对当前几条成立，也需要对整批数据断言，而不能只凭字符串拼接思维。

优先使用明确的模板生成区域或经过验证的completion mask。若自己构造边界，必须验证prompt token确实是完整序列的前缀，失败就停止。对每个审核样本打印：位置、token ID、解码片段、attention值、label是否忽略。单个token的解码片段可能不是完整汉字，最终还要检查监督片段整体解码。

回答区域审核的核心问题只有三句：该学的答案都在吗？不该直接监督的提示混进去了吗？最后一个目标token是否仍有正确前文？这比“训练器没有报错”强得多。

## 7．长度、截断、padding和packing

字符数不等于token数。统计完整模板长度、提示长度、有效回答长度的分布，至少记录最大值、几个分位点和超限条数。先看真实分布再选max\_length，不先拍脑袋用固定长度然后默默丢答案。

若完整序列1200 tokens，而上限1024，右截断可能切掉位于末尾的回答；左截断可能保住回答却删去tools\_enabled或前轮project。两者都不自动正确。本课遇到超限记录先隔离，检查能否删去无关上下文；确需缩短时重新验证语义与标签，并记录策略。

padding是凑齐batch的长度，padding位置不参与损失。packing是把多条记录装进更长序列，节省空位，但必须核查样本边界、位置索引、注意力隔离与回答mask是否符合所选实现。第一轮关闭packing，先建立容易读懂的单样本正确路径；第5课再用同口径实验决定是否开启。

不要把“padding很多”直接诊断成“模型训练差”。它首先是效率问题；只有mask或注意力处理错误时才可能改变监督语义。两种问题应该分别排查。

## 8．亲手完成一个数据审计

按这个顺序做：

1. 从第1课12条教学样本构建事实层文件，注明它们仅是公开开发材料。
2. 写字段校验，故意加入重复ID、空owner、错误decision和同组跨split，确认都能被发现。
3. 固定模板构造器，渲染四类代表样本；核对禁用字段与多轮历史。
4. 在可用tokenizer上统计长度，保存超限ID，不静默丢弃。
5. 获取训练实际使用的batch，逐位置查看labels，确认有效目标数大于零。
6. 解码有效目标，人工比对target；把pad与eos共ID情况单列测试。
7. 冻结manifest。任何后续改动都产生新数据版本，而非覆盖旧版后继续复用成绩。

完成门槛不是“文件存在”，而是每个检查都能展示一个应该失败的反例和一个应该通过的正例。配套notebook若尚未运行，只勾“代码已写”，不能勾“审计通过”。

## 9．练习与答案

**练习一：** 用户缺owner，审计字段case\_type写missing\_owner；构造器把整个记录转成文本送入模型。风险是什么？

**答案：** 标签元数据泄露，模型可读case\_type直接决定追问。只将任务真实需要的规则、环境与消息放入输入，审计字段留在旁路。

**练习二：** prompt不参与loss，所以可把其attention\_mask置零吗？

**答案：** 不可这样等同。模型仍需要读取prompt才能回答；loss忽略与输入不可见是两件事。使用labels的忽略位置控制监督。

**练习三：** 只要每条至少剩一个有效label，就证明截断没问题吗？

**答案：** 不成立。可能只剩一个大括号，或丢了条件与结束符。还需验证完整目标及必要上下文，统计截断后的实际内容。

**练习四：** 禁用题的目标是answer，但大多数训练例子是call。可否复制禁用题一百遍平衡？

**答案：** 可以改变曝光权重，却不会产生一百个独立场景，且可能导致正常输入过度拒绝。先记录组数、重复权重，再用验证集检查两边行为，不把条数当多样性。

**练习五：** 保存tokenizer名称够不够？

**答案：** 不够。需要revision、实际模板、special token配置及任何本地修改。相同名称日后可能取到不同文件，本地模板也可能被训练脚本覆盖。
